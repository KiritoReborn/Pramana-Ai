# Bugfix Requirements Document

## Introduction

The Next.js frontend application (located in the `frontend/` folder) is currently a non-functional UI mockup that is completely disconnected from the existing Python/Streamlit backend. The frontend displays a government e-procurement portal interface styled after the Karnataka government portal, but all buttons, navigation, pages, and workflows are broken with no backend integration. This bugfix addresses the complete integration of the frontend with the Python backend to create a fully functional procurement system.

**Impact**: The frontend is unusable for actual procurement workflows. Bidders cannot upload documents, officers cannot run evaluations, and no real data flows between the UI and the backend processing engines (document processing, LLM extraction, evaluation engine, rule engine, report generation).

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN a bidder clicks the "Choose Files" button in the Document Upload Portal THEN the system does nothing and no files are sent to the backend

1.2 WHEN a bidder clicks the "Start Upload" button THEN the system only shows a toast message and does not process documents through the Python backend

1.3 WHEN a bidder clicks the "Apply" button on a tender THEN the system only sets local state and does not fetch tender details from the backend

1.4 WHEN an officer clicks "Upload Master Document" in Tender Configuration THEN the system does nothing and the tender is not processed by the backend TenderProcessor

1.5 WHEN an officer views the Evaluation Matrix THEN the system displays hardcoded mock data instead of real evaluation results from the backend

1.6 WHEN an officer clicks "Review Case" on a "Needs Review" bidder THEN the system opens a modal with mock data instead of actual evidence from the backend retrieval engine

1.7 WHEN an officer clicks "Confirm Override" in the review modal THEN the system only updates local state and does not persist the override to the backend audit logs

1.8 WHEN an officer clicks "Export Final PDF Report" THEN the system downloads a mock text file instead of a real PDF generated by the backend ReportGenerator

1.9 WHEN any user navigates between pages (dashboard, tenders, uploads, submissions, review, reports) THEN the system only changes local view state and does not fetch data from the backend

1.10 WHEN the frontend application starts THEN the system does not establish any connection to the Python backend API

1.11 WHEN a bidder uploads documents THEN the system does not send files to the backend DocumentProcessor for OCR, text extraction, and FAISS indexing

1.12 WHEN an officer triggers evaluation THEN the system does not call the backend EvaluationEngine to run the actual evaluation workflow

### Expected Behavior (Correct)

2.1 WHEN a bidder clicks the "Choose Files" button in the Document Upload Portal THEN the system SHALL open a file picker and allow selection of PDF, PNG, JPG, JPEG files

2.2 WHEN a bidder clicks the "Start Upload" button with selected files THEN the system SHALL send the files to a Python backend API endpoint that processes them through DocumentProcessor and indexes them in FAISS

2.3 WHEN a bidder clicks the "Apply" button on a tender THEN the system SHALL fetch tender details from the backend API and display the extracted eligibility criteria

2.4 WHEN an officer clicks "Upload Master Document" in Tender Configuration THEN the system SHALL send the PDF to the backend API which processes it through TenderProcessor and extracts eligibility criteria

2.5 WHEN an officer views the Evaluation Matrix THEN the system SHALL fetch real evaluation results from the backend API and display actual bidder scores, statuses, and evidence

2.6 WHEN an officer clicks "Review Case" on a "Needs Review" bidder THEN the system SHALL fetch the actual evidence chunks, extracted text, and confidence scores from the backend API

2.7 WHEN an officer clicks "Confirm Override" in the review modal THEN the system SHALL send the override verdict and justification to the backend API which persists it to audit logs and recalculates the final verdict

2.8 WHEN an officer clicks "Export Final PDF Report" THEN the system SHALL call the backend API to generate a PDF using ReportGenerator and download the actual PDF file

2.9 WHEN any user navigates between pages THEN the system SHALL fetch the appropriate data from the backend API for that view

2.10 WHEN the frontend application starts THEN the system SHALL establish a connection to the Python backend API and verify it is available

2.11 WHEN a bidder uploads documents THEN the system SHALL send files to the backend which processes them through OCR, text extraction, table extraction, and FAISS indexing, then return processing status

2.12 WHEN an officer triggers evaluation THEN the system SHALL call the backend API which runs the full evaluation workflow (retrieval, LLM extraction, rule engine) and returns the evaluation results

### Unchanged Behavior (Regression Prevention)

3.1 WHEN the frontend displays the government portal styling (Karnataka emblem, color scheme, bilingual support) THEN the system SHALL CONTINUE TO maintain the existing visual design and government portal aesthetic

3.2 WHEN users interact with the font size controls (A-, A, A+) THEN the system SHALL CONTINUE TO adjust the font scale as currently implemented

3.3 WHEN users toggle between English and Kannada language THEN the system SHALL CONTINUE TO update the language state and display the selected language

3.4 WHEN the frontend displays the role selection page (Bidder vs Officer) THEN the system SHALL CONTINUE TO show the same UI and role selection logic

3.5 WHEN users navigate using the sidebar menu (Bidder Menu or Officer Menu) THEN the system SHALL CONTINUE TO update the active view state

3.6 WHEN the frontend displays notices, quick links, and navigation items THEN the system SHALL CONTINUE TO render these UI elements as currently implemented

3.7 WHEN the frontend shows toast notifications THEN the system SHALL CONTINUE TO display temporary toast messages at the bottom of the screen

3.8 WHEN the frontend displays the review modal overlay THEN the system SHALL CONTINUE TO show the modal with the same layout and styling

3.9 WHEN the Python backend processes documents through the existing Streamlit app THEN the system SHALL CONTINUE TO function independently without breaking existing functionality

3.10 WHEN the Python backend generates reports, runs evaluations, and logs audit trails THEN the system SHALL CONTINUE TO perform these operations as currently implemented in src/ui/app.py
